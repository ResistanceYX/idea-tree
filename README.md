# idea-tree

> 每个点子只死一次，但死因可以被检索一万次。

这里是一座创业点子的死法档案与科技树。每个节点记录：点子一句话、死因分类、证据链接、可拆零件、死因保质期。

**适合谁**：
- 正在进行创业点子验证、点子评估或项目复盘的人，以及寻找失败案例、创业避坑经验和可复用零件的团队。
- 本项目也预期各类AI将成为未来的重要用户：AI可以读取结构化节点与索引，辅助相似风险检索、事前预审和更新建议；涉及入库与判断性修改时，仍由人类审核定案。

**预审与验尸**：
- 仓库同时包含两类档案。
- “预审”是基于公开证据与推演的事前判断，不是已经发生的失败；
- “验尸”来自真实实施、停止、失败或转向记录，不以纯粹假设替代实际经历。
- 详细定义见[节点格式](#节点格式-v110)。

**怎么使用**：

- 1. 提出点子后，先在[全量索引](INDEX.md)或[nodes/节点目录](nodes/)检索相似节点。
- 2. 核对死因、证据链接、置信度、备注和死因保质期，判断其结论与边界是否适用于当前点子，不把预审当成真实失败事实。
- 3. 决定是否需要新增或更新档案；已有真实实施、停止、失败或转向记录时，可按验尸回写。

- **工作方式**：AI初稿，人类审核定案。
- **全量索引**：[INDEX.md](INDEX.md)（由节点自动生成的检索目录与死因统计，请勿手工维护节点数据）。
- **公开静态索引站**：[idea-tree 静态站](https://resistanceyx.github.io/idea-tree/)（由 `nodes/*.yaml` 自动生成，支持检索、组合筛选与单节点档案页；通过
  GitHub Pages 工作流更新）。
- **科技树关系图**：[科技树页](https://resistanceyx.github.io/idea-tree/graph.html)（由正式节点的“相关节点”双端声明自动派生；`graph.html` 与
   `data/graph.json`均由生成器维护。直接派生显示方向，一般相关不显示方向，孤立节点保留在完整列表与可选图形分组中；不按id形态、标题或抽象相似性推断关系）。
- **简易实现仓库**：[IMPLEMENTATIONS.md](IMPLEMENTATIONS.md)（登记与正式节点对应的独立实现仓库及其实现范围；仓库名统一使用节点带编号文件名主体`<编号>-<id>`，
  登记不代表节点目标已完整实现）。
- **离线备份与恢复**：[BACKUP.md](BACKUP.md)（月度U盘备份的范围、执行记录与恢复方法）。
- **死因保质期复核**：[REVIEW.md](REVIEW.md)（由节点与人工复核记录自动生成；新节点自动进入待复核清单，复核结论写入[review_records.yaml](review_records.yaml)，
  请勿手工编辑表格）。
- **决策时段建议**：涉及判断性的修改（复活状态、置信度、分类法变动），尽量避免在凌晨0点至5点定案，可等次日清醒后斟酌执行。

## 节点格式 v1.10

示例：
- 首个节点／历史示例：[大肥鱼赛博墓地](nodes/0001-dafeiyu-cyber-cemetery.yaml)
- 死透节点示例：[AI游戏修改器及其平台](nodes/0008-ai-game-modifier-platform.yaml)
- 复活候选节点示例：[AI生成红色题材中小体量视觉小说](nodes/0009-ai-red-visual-novel.yaml)
- 机构部署与多源证据示例：[AI拦截仿真对话反诈Agent](nodes/0015-ai-scam-interception-agent.yaml)
- 开源实现与风险边界示例：[大肥鱼消除计划](nodes/0025-dafeiyu-cleaner.yaml)
  
格式：
- 编号: 正式节点必填的永久档案序号，值必须为带引号的四位十进制字符串，如"0001"；普通节点从"0001"开始，"0000"永久保留给未来的idea-tree元节点。
  未上传的本地工作稿可暂不填写，但不得自行补号、占位或预约号码
- id: 全小写、全局唯一。普通节点仅使用英文、数字和连字符；直接派生节点可以在各层母题id与子题短名之间使用下划线，下划线仅用于表示派生层级，不得用于普通命名。
  直接派生节点还须遵守下文“母题前缀规则”
- 标题: 节点在档案、索引和科技树中展示的人类可读名称，应简明概括点子的对象与产品形态，可使用中文、产品名和必要限定语；
  标题供人阅读，id供程序检索与表达派生关系，两者不要求逐字对应
- 一句话: 对点子的一句话描述
- 档案类型: 预审 | 验尸。预审指对尚未实际执行、缺少真实失败记录的点子，依据公开证据与内部推演预判死法；验尸指对已有真实实施、停止、失败或转向记录的点子，依据一手
  经历或公开资料复盘。预审不得写成已经发生的失败，验尸不得只用假设代替实际经历
- 复活状态: 死透 | 复活候选 | 已复活
- 结论边界: 可选的非空字符串，用一句话限定当前结论或复活范围，不重复整段论证，不记录新证据、日期或状态历史；公开详情页对复活候选与已复活节点显示为“复活范围”，其
  他状态显示为“结论边界”（v1.9 新增）
- 重启预算: 低 | 中 | 高（可选字段，低、中、高分别对应0至1万元、1至100万元、100万元以上三档）
- 死法: 每条含 类型（必须为上表之一）/ 证据 / 推理 / 置信度；证据为"创始人自我分析"时可用 分析: 替代 推理:，并允许省略 案例 与 证据链接
- 需求证据: 需求仍存活的一手证据；未观察到需求时填类型: 暂无需求作为审计记录，附件存evidence/目录并保留原始文件名（可选字段）
- 商业及社会价值评估: 评估谁受益、谁付费、收入与成本是否可能匹配，以及公共、文化、教育等社会价值；没有证据时明确写“未验证”，不得把社会价值直接等同于商业可行性，
  也不得编造市场数据。死透节点可选，复活候选与已复活节点必选
- 可拆零件: 点子死后仍可拆用的部件（功能模块、工作流、Prompt包、数据、洞察）；零件长大后可独立成节点，用"相关节点"字段挂接
- 相关节点: 相关节点列表，每条含 节点/关系/可选说明，双向声明（可选字段）；“节点”填写目标节点的带编号文件名主体，即`<编号>-<id>`，不带`.yaml`扩展名
- 死因保质期: 即建议复核日期，一律写YYYY-MM-DD，不得晚于审核日期起五年；晚于三年者须在节点内备注说明原因。具体判断遵守下文“死因保质期判定规则”，不得无依据默认填
  写审核日期起一年（v1.10修订）
- 起草AI: AI辅助起草需署名
- 审核人：即审核者GitHub用户名
- 审核日期：一律写YYYY-MM-DD
- 备注: 节点级可选补充说明，用于记录适用范围、证据边界、定性限制、特殊复核原因及其他不宜写入死法正文的补充信息；不得替代必选字段、证据、
  证据链接或商业及社会价值评估，也不得与正文结论冲突。一般为可选字段，但死因保质期晚于审核日期起三年等既有规则明确要求说明时仍须填写

新增字段必须更新本表并提升版本号

## 编辑规范（十三条铁律） v1.8

- 1.**证据铁律**：每条死法必须有证据；纯内部推演须注明，公开案例必须挂链接。
- 2.**置信度规则**：纯内部推演封顶“中”；有公开证据链接并满足第5条的来源数量与独立性要求，才可标“高”。
- 3.**标点与语法**：正文用中文全角标点；YAML键值对用半角冒号加空格，同级缩进对齐。
- 4.**链接复用规则**：同一证据来源可被多条死法复用，但每次复用都必须直接支撑对应死法；非必要不重复，尤其不得用共同来源替代针对本节点或本层新增机制的证据。
- 5.**孤例不证**：案例分析至少含两个相互独立的证据来源方可标“高”置信度。同源变体只计一个来源；两个不同URL只是技术下限，不自动证明来源独立或足以支持高置信度。
- 6.**引用上限**：若节点死法数量为n，同一证据来源（含同源URL变体）的引用次数不得超过n-2，不得通过更换链接形式规避。
- 7.**链接数量规则**：单个死法的证据链接数量原则上不超过8个；特殊情形最多不超过16个，超过8个须在死法条目内备注说明原因。
- 8.**备注清理规则**：版本备注仅保留当前及前一版本备注；每次升版时删去更早的备注，历史沿革以 commit 记录为准。
- 9.**链接可访问性规则**：证据链接须公网可直接访问；付费墙、会话校验、下载接口类链接不得作为证据链接，可写入死法说明或摘录卡备查。
- 10.**节点正式名称规则**：项目内部使用的数字编号、字母等简单代称（如13号、14号、15号、19号、A、B、C）仅限对话交流，不得作为节点名称写入仓库正文；替代这些代称
  时，叙述文字使用对应YAML“标题”字段的正式标题，id保持不含编号，“相关节点”的“节点”字段使用目标节点的带编号文件名主体，文件名按“永久编号规则”与编号、id对应。新增
  或修改节点时同步检查旧节点、双向关系说明与README；B站、B轮、B端、C端、Series-B、A-35等非节点代称不得误改。
- 11.**永久编号规则**：正式节点的编号分配、文件名前缀与退役登记必须遵守下文“永久编号规则”；编号与id职责分离，不得把编号写入id，也不得由生成器自动补号、猜号或重
  排。（v1.7 新增）
- 12.**同源归并规则**：同一页面、同一作品或同一研究成果的不同URL形式，在高置信度来源计数与n-2检查中只算一个证据来源；自动归并与人工判定边界遵守下文“同源证据归并
  与节点簇多样性”，不得利用锚点、跟踪参数、平台移动页、短链、镜像、转载、翻译、版本号或发布页变体制造虚假多样性。（v1.8 新增）
- 13.**节点簇证据多样性规则**：直接派生子题原则上至少增加一个未用于任何祖先节点、且直接支撑本层新增机制的不同证据来源；显式相关节点也应有各自针对特有机制的直接
  证据。共同基线可以必要复用，但不得替代子题或关联节点自身的证据；确实没有新增公开证据时，由主编确认并记录证据缺口，不得用同源变体或弱相关链接凑数。（v1.8 新增）

新增编辑规范必须更新本表并提升版本号

### 同源证据归并与节点簇多样性

“同源”用于判断证据独立性和复用集中度，不等于两个页面逐字相同，也不等于同域名、同作者或同项目。应按“确定的形式归并＋人工内容判断”分层处理：

- **可确定归并的形式**：主机名大小写、默认端口、片段锚点、明确跟踪参数等不改变来源身份的差异；GitHub同一所有者、仓库、引用与文件路径的`blob`／`raw`形式；arXiv
  同一论文标识的`abs`／`html`／`pdf`及版本后缀；DOI重定向主机形式；B站同一BV／av号及相同分P，YouTube同一视频标识的常见观看路由。校验器据此生成“同源证据键”，
  http／https及普通跟踪参数差异不产生新来源。B站不同分P不自动归并，GitHub不同文件、引用或仓库路径不自动归并。
- **必须人工判断的形式**：无法直接识别目标的短链或重定向、镜像、转载、翻译、DOI与出版商页面、预印本与正式发表版、不同论文版本及同一研究的不同报道。确认指向同一
  作品、同一报道或同一研究成果时，不得把它们当成相互独立验证；比较版本差异时可以分别引用，但仍须说明它们不是独立来源。短链未核实目标前不得猜测归并。
- **不得机械判同或判异**：同一域名、作者、机构、项目或标题不必然同源，同一仓库的不同文档可以支撑不同事实；不同域名、作者或页面也不必然独立，转载同一稿件
  仍只有一个原始信息源。应核对实际内容、原始数据、采编或实验过程及引用链。人工归并若影响高置信度或n-2判定，须在对应死法备注或节点备注写明归并对象与理由。
- **节点内执行**：单条死法中的重复或同源变体链接只计一个来源并产生警告；高置信度按归并后来源数检查，n-2按同一来源在节点内的引用总次数检查。校验汇总同时保留“不同
  原始链接”和“归并后来源”两个口径，不以归并数篡改原始链接出现次数。
- **节点簇执行**：母题与子题确需共同描述同一基础机制、遵循同一官方约束或使用同一数据集时，可以复用共同基线；但子题新增的限制、组合、执行环境或工作流必须另有直接
  证据。显式相关但非直接派生的节点同样不得只换产品表述而整套沿用来源。独立来源数量不是质量配额，不得为满足数量加入弱相关材料。
- **自动提示边界**：显式相关节点对共享至少4个同源来源，且共享数占较小节点不同来源数至少50%时，产生人工复核警告；同一来源沿显式相关关系链覆盖至少4个节点时，另产
  生跨节点复用警告，以防“每对只共享一个来源”绕过节点对检查；直接派生子题的不同来源全部已见于祖先链时，再产生新增来源警告。警告不阻断校验，不证明复用不合理，
  也不授权AI自动换链、删证据或调整置信度；主编可以确认必要复用并保留警告理由，也可以补充或替换真正更直接的证据。
- **无全局限额**：不设置“全仓每个链接最多出现几次”或按域名分配数量等硬上限。必要性、直接性和独立性必须结合实际论断判断；自动键不同不证明内容独立，自动键相同也不
  替代人工对具体论断适用性的审查。

### 执行人限制的评价姿态

“执行人限制”用于分析实施条件如何影响项目，不用于评价或贬损执行者本人，也不默认以主编本人的时间、能力和预算代表所有实施者。

- **预审**：以明确说明资源条件的普通个人或小团队为参照，分析项目实施所需的时间、能力、资金、团队、资质、渠道与持续维护条件。不得只写“普通人做不了”“创始人能力不
  足”或“没有资金”，应说明具体限制及其适用范围。
- **验尸**：依据项目方真实的实施、停止、失败或转向记录，写明项目方实际受到的限制及其影响。不得将某一项目方的个案条件直接推广为所有团队的共同死法。
- **因果链**：每条执行人限制应说明“具体限制→受影响的关键工作→项目后果”。仅存在资源不足或能力差异，不足以直接判死。
- **边界与缓解条件**：如通过学习、外包、合作、增资、工具替代或缩小实施范围可以降低影响，应在推理或分析中写明；可缓解的限制不得包装成无条件死局。
- **个案保留**：主编本人或特定项目方的真实约束可以作为具体案例保留，但应明确其个案属性，不作为其他实施者的默认条件。

预审可使用以下句式：

> 对【明确资源条件】的个人或小团队，【具体限制】会使【关键工作】难以【完成或持续】，从而可能导致【项目后果】；若具备或采用【缓解条件】，该限制的影响将降低。

验尸可使用以下句式：

> 项目方的【实施、停止、失败或转向记录】显示，【实际限制】导致【关键工作】未能完成或持续，最终造成【实际结果】；该结论适用于【案例边界】，不直接推广至其他团队。

执行人限制仍须遵守既有证据、推理或分析及置信度规则；评价姿态的变化不降低证据门槛，也不允许脚本自动修改相关判断。

### 死因保质期判定规则

- 死因保质期应依据核心结论所依赖的最短关键变化窗口确定。先识别可能推翻或明显改变当前结论的技术、平台、价格、政策、需求、供应与执行条件，再决定应在何时之前复核；
  不得直接复制同批、相邻、同类或上一节点的周期。
- “审核日期＋一年”只是可能出现的候选结果，不是默认值。AI交付初稿时必须另行说明保质期建议依据，至少回答“哪项关键条件可能发生变化”及“为什么选择在该日期复核”；
  不得以“通常一年”“与其他节点一致”或“避免过早到期”作为理由。
- 下列周期仅作量级参考，不是可以跳过判断直接选择的菜单：已知近期政策、平台、模型、价格或项目里程碑等变化时，通常安排3至6个月；关键条件变化较快但没有明确事件时，
  可考虑6至12个月；关键需求、物理约束、历史事实或结构性限制较稳定时，可考虑1至3年；超过3年仍须具备针对本节点的稳定性依据并按既有规则备注。
- 一个局部条件变化较快，不等于整个节点都必须采用最短周期；只有该条件足以改变核心死法、复活状态或结论边界时，才以其作为关键变化窗口。
- 无法形成可靠判断时，AI应明确说明不确定性并提出保守的临时建议，由主编审核定案，不得回填一年凑齐字段。
- 既有节点的死因保质期只能在实际复核后调整；不得因本条规则、同批节点趋同或月度技术全检而批量缩短、顺延或重新设定日期。

### 永久编号规则

- **分配时点**：普通节点编号只由其首次进入云端`main`分支`nodes/`目录的顺序决定。Issue建立、清单登记、AI起草、本地保存和PR创建均不产生正式编号；编号分配是入库决
  策，由主编确认，生成器不得自动补号、猜号或重排。
- **字段与文件名**：正式节点须在YAML顶层填写`编号: "0001"`形式的四位字符串，文件名统一为`<编号>-<id>.yaml`。未加引号导致前导零丢失、编号与文件名不一致或继续使
  用无编号旧文件名，均属于校验错误。
- **职责边界**：编号不写入YAML的`id`字段。`id`继续作为节点内部标识、复核记录与公开详情页URL的主键，`标题`继续作为正式名称；`相关节点.节点`统一填写目标节点的带编
  号文件名主体`<编号>-<id>`，公开详情页仍使用`nodes/<node-id>.html`。
- **不可变与退役**：正式分配后，标题、id、死法、复活状态或正式区内文件位置变化均不换号；id修改时保留原编号。节点删除、被吸收合并或迁出正式区后，其编号退役且不得
  复用；下一号为历史已分配最大普通号加一，计算时必须包含持久保留的退役记录，`0000`不参与普通节点最大号计算。
- **同批顺序**：同一提交内的节点顺序由主编依据原始上传清单或本人确认确定，不得按文件名、标题、id或INDEX顺序伪造；并行PR以实际进入`main`的先后为准，后合并者须重
  新复核编号。
- **独立取号与储备区**：直接派生节点独立取得普通编号，不使用`0001.1`等层级编号。`non-startup-tech/`不参与编号，储备档案首次正式进入`nodes/`时才按当时顺序取号。
- **`0000`保留**：`0000`永久保留给未来的idea-tree元节点；当前只保留号码，不创建空壳YAML，不计入节点统计，不进入INDEX、REVIEW、静态站或公开JSON，也不触发阶段阈
  值。未来真正起草元节点时另行确认其结构与统计口径。
- **工作稿**：未上传工作稿可以暂不填写`编号`，不得以候选号占位、锁号或预约号；正式上传前由主编按当时云端分配记录和本批顺序确定号码。
  
## 母题前缀规则

- 母题前缀只表达直接派生关系，不替代“相关节点”双向声明。直接派生节点必须在“相关节点”中声明直接母题，母题端同步声明对应派生关系；完整祖先链通过这些直接关系逐跳追
  溯，不得仅凭id推断全部层级。
- 多层派生的id最多保留直接母题与再上一级母题两段前缀，再加上本子题短名，更早祖先不再累加。例如：`a` → `a_b` → `a_b_c` 后，下一级使用 `b_c_d`，再下一级使用
   `c_d_e`。这里的“上两级”明确指直接母题和直接母题的母题。
- 各层短名只写本层新增的核心区别，不重复母题中的共同修饰语。保留两段前缀后仍须保证全局唯一、简洁、可检索；发生重名或歧义时，应调整子题短名，不得通过恢复完整祖先
  长链解决。
- 存量节点可以在节点数量较少时统一改名；改id必须同步更新带编号文件名（保留原编号）、README链接、相关节点引用及本地附件路径，不能只改id。本条不构成对既有节点的批
  量改名授权。
  
## 月度全检

主编每月至少使用AI对项目进行一次全检。全检应以当时最新云端 `main` 的新鲜副本为基线，记录检查日期、提交哈希、正式节点数、死法数、错误与警告数量及人工待办；不得在
混入未上传工作稿、候选节点或其他实验修改的目录中直接得出“云端全检通过”的结论。本地检查通过后，仍须核对最终云端提交及部署结果。

- **结构与编号**：检查全部正式节点YAML解析、必选字段、枚举、编号与文件名、内部id、相关节点引用与双向声明、日期、本地路径与附件，以及README和已拆分维护文档的内部
  链接；核对“编号—文件名—内部id”三者一致，检查现役重复编号、生成器自动改号风险及编号登记机制是否被绕过。
- **退役号与历史边界**：持久编号登记机制实施前，退役号复用、历史最大号和节点首次入库顺序只能结合Git历史与主编确认人工核对，不得仅凭当前 `nodes/` 目录宣称历史审
  计通过；登记机制实施后，再同时检查登记记录、现役节点与自动防复用校验。
- **标准验证**：运行仓库现行完整测试、正式节点校验、INDEX／REVIEW生成与 `--check` 一致性检查及静态站构建。INDEX.md和REVIEW.md由生成器维护，不手工修改其中统计或
  清单。
- **复核机制**：核对 `review_records.yaml` 的解析、记录主键、复核日期、结论和证据边界，检查REVIEW中的到期、临期与待复核条目，以及“当前复核周期分布”的基准日期、
  分档和合计：有实质复核记录的节点以最新“复核后日期”为基准，其余以“审核日期”为基准，合计必须等于正式节点数。若“一年”等单一档位异常集中，或同批节点无理由共用相同
  周期，应列为路径依赖警告并抽查判定理由；分布异常只提示人工复核，不得自动改日期，也不得把恰好一年本身判为错误。新节点没有人工实质复核记录时显示“待复核”属于正常
  状态，不得为消除该标记而虚构复核履历。
- **链接与证据**：检查链接复用、格式与可访问性，核对同源变体是否被用于规避高置信度双来源或n-2限制，逐项处理相关节点簇集中度及直接派生子题新增来源警告，并抽查共
  享来源是否确属必要共同基线、各节点特有机制是否有直接证据。区分公开可访问、访问受限和确认失效；403、412、超时、反自动化或工具访问受限不等于链接失效，应交由主编
  人工复核。不得为完成全检而绕过登录、验证码、付费墙、访问控制或平台限制，也不得仅为清零警告改用弱相关链接、删除必要基线或机械调整置信度。
- **语义一致性**：检查相关节点说明与备注、复活状态与结论边界、证据与推理之间是否存在明显冲突。自动校验通过不等于语义一致；发现判断性问题时只列出修改建议，由主编
  审核定案。
- **云端与公开站**：核对最终提交的校验和Pages工作流状态，抽查公开首页、科技树页、节点详情页及 `data/nodes.json`、`data/graph.json` 的节点数量、编号、关系和
  日期是否同步；科技树还须核对去重关系数、派生方向、双端说明和孤立节点数量，确认图形增强失效时完整静态列表仍可用，且 `evidence/`、备份材料、访问凭证及其他非公开
  内容未进入公开产物。
- **储备区隔离与导航**：`non-startup-tech/` 不属于月度全检所称的正式节点YAML，不逐条重做其实质审查；其内容不得纳入正式节点编号、统计、INDEX、REVIEW、公开JSON、
  首页搜索或正式节点详情页。经主编确认的标题和一句话可通过 `non-startup-tech/00-public_reserve.yaml` 中的显式白名单进入独立“非创业技术储备”导航页；该页只提供
  GitHub原文链接，不复制完整YAML，也不表示储备稿已经通过实质审核。全检须核对白名单登记、实际公开范围与上述隔离边界。
  
月度全检是技术、链接、生成物、公开隔离和明显语义冲突检查，不等于每月对全部节点重新进行死因实质复核。AI不得在全检中自动修改复活状态、置信度、档案类型、死法类型或
商业及社会价值评估等判断性内容；不得仅因完成全检而顺延审核日期或死因保质期，也不得把技术全检记录写成人工实质复核。判断性修改仍按“AI初稿，人类审核定案”执行。

## 投稿

开一个 Issue，按上述格式填写。正式上传前须由主编根据当时云端分配记录和本批顺序确定号码，写入带引号的四位`编号`，并将文件重命名为`<编号>-<id>.yaml`；同批上传须在
上传说明中列出有序节点清单，并行PR按实际进入`main`的先后重新复核。本地工作稿不得提前占用正式号码。
