# 维护事件日志

本目录按年月归档 idea-tree 的代码、工作流、静态站、公开数据生成与部署维护记录。日志保存“为什么改、怎样实施、遇到什么故障、如何修复、最终如何验证”，供后续维护复用经验。

本目录不替代 Git 提交、Issue 或特别鸣谢：Git 保存精确差异，Issue 保存计划与讨论，特别鸣谢按助手记录贡献，维护日志则按一次完整维护事件保存技术过程和结论边界。

## 记录范围

1. 对 `scripts/`、`site/`、`.github/workflows/`、`tests/`、公开数据生成逻辑的实质修改，以及部署故障与恢复，必须记录。
2. 普通节点内容更新没有特殊维护问题时不强制单独记录；发生双向关系、自动流、公开站同步或证据处理等可复用问题时可记录。
3. 同一逻辑修改产生的多个上传提交、修复提交、索引自动提交和部署重跑合并为一篇日志，不按 commit 数量重复建文。
4. 纯错别字修正及已经并入同一维护事件的自动生成提交不单独记录；独立事件才另建新文件。
5. 一篇日志必须区分本地验证、云端校验、Pages 部署和公开站验收。本地通过不等于入库或上线，历史失败也不等于当前仍失败。

## 目录与命名

```text
MAINTENANCE/
├── README.md
└── YYYY/
    └── MM/
        └── YYYY-MM-DD-简短英文主题.md
```

- 日期采用维护事件开始日期；跨月或跨天完成时不移动原文件，在完成日期与正文中补足实际过程。
- 同日多个独立事件用不同主题名区分；主题使用简短英文小写和连字符，中文标题写在文件正文中。
- 不设置维护日志流水编号，避免与节点编号、Issue 编号及特别鸣谢工作记录编号混淆。
- 年月目录不再放置需要手工同步的 README 或统计文件；本文件只维护规则与模板，不复制日志总清单。

## 写作与更新规则

1. 每篇按“背景与目标—变更范围—实施与验证—问题、根因与处理—最终结论与边界—后续事项”组织，只保留必要摘要和可复查链接，不复制完整 diff、网页全文或冗长原始日志。
2. 变更范围须列实际源文件；`INDEX.md`、`REVIEW.md`、公开 JSON 和静态站页面等生成物单独注明，不冒充手工修改。
3. 问题尽量按“现象—根因—修复—验证”记录。根因未完全确定时明确写不确定性，不把时间相关或服务端错误武断归因于仓库内容。
4. 状态使用“进行中”“已完成”“部分完成”或“待跟进”。只有对应范围内的实际验收完成后才能标记已完成；不得用预期结果填充最终提交、运行编号或公开站结论。
5. 后续实质更正应保留原事件历史，并追加带日期、提交和证据的更正说明；不得通过删除失败经过制造一次成功的假象。链接或文字勘误可直接修复，但不得改变原事件结论。
6. 本目录文件中的根仓库相对链接以文件位置为起点；年月下的日志返回根目录使用 `../../../`，本 README 使用 `../`。Issue、Actions、提交及外部资料使用完整 HTTPS 链接。
7. 本目录位于公开仓库，内容公开可见。不得写入 API Key、Cookie、token、秘密值、私有地址、未授权代码、个人敏感信息或完整私有日志；错误只保留经过清理的必要摘要。
8. 本目录当前不自动进入公开静态站，不因此新增 CI 校验或索引生成器。未来确需公开展示、检索或自动目录时另行评估，不把自动化作为写日志的前置条件。
